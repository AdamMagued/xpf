# #12185 — IPv6 BGP peer with family inet

- **Timestamp**: 2026-10-11 (`fix/12185-campaign-pub`, base `4a17e0d29`)
- **Action**: reject explicit per-neighbor `family inet` on IPv6-addressed BGP peers at strict compile; tolerant loads warn and leave that family inert, explicitly disabling FRR's default IPv4-unicast activation.

## Red before

The STEP-0 render on `a714c90d4` compiled `2001:db8::9 family inet` with `FamilyInet=true`, then emitted only the neighbor's `remote-as` declaration: no address-family block, activation/deactivation, import/export route-maps, or prefix-limit. The policy-bearing peer therefore had no renderer-owned AF entry while FRR could default-activate IPv4 unicast.

The regression cells were added and run before the implementation. They were RED: strict compilation accepted the cross-family shape; lenient compilation retained `FamilyInet=true` with no #12185 warning; the FRR render cell had no fail-closed deactivation.

## Change

- The #2454 group-family gate and `applyBGPNeighborProps9192` share the
  `FRRAddrFamily` predicate. IPv4-mapped literals classify as IPv6 for inherited
  families and explicit per-neighbor `family inet` checks. Strict compilation
  rejects the explicit declaration; tolerant compilation warns, records
  `CrossFamilyInet`, and clears any inherited `FamilyInet`.

  Tolerant per-neighbor handling still collects independent unsupported-SAFI
  diagnostics and finalizes their activation wording against the merged
  neighbor state (#11815).
- The FRR AF classifier treats this marker as an unrenderable family. For an
  inet-only IPv6 peer, tolerant render emits `no neighbor <peer> activate`
  under IPv4 unicast and does not default-activate it under IPv6. A separately
  declared inet6 family remains independent.
- Regression coverage includes strict/lenient mapped group inheritance,
  render policy placement/deactivation, and a `vtysh -C` grammar-only parse
  with an invalid-command negative control (not a live BGP config load).
