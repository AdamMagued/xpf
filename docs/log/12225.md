# Issue #12225 — keep AppID-on/off labels aligned for unreferenced overlaps

## Why

When AppID was disabled, the tuple fallback considered every configured user app, but `appNames` contained only policy-referenced names. An unreferenced app whose natural ID collided with another app therefore fell back to its natural hash instead of the ID assigned from the full AppID-on catalog. For the `svc-217`/`svc-396` collision, this could select a different app than AppID-on; with the pair alone, strict `<` also left equal-ID ties dependent on Go map iteration order.

## What changed

- Build a per-request `appid.FallbackIndex`: O(1) natural-ID collision checks
  cover predefined and user names, and a lazily cached full-universe assigned-ID
  map is reused for repeated colliding-tie renders. Session-list, gRPC filter,
  top-talkers, and CLI paths pass the index through the resolver variants.
- Re-rank only same-tier collision ties that include an uncatalogued candidate;
  fully catalogued ties retain the AppID-off catalog's assigned-ID winner so
  fallback labels remain consistent with existing off-mode stamps.
- Add focused cells for predefined collisions, five-name mixed ties, mixed
  specificity tiers, referenced S14/S16 stamp consistency, and 50 quiet
  colliding renders. Pin a warmed colliding-tie render at zero allocations.

## Risk

The index build hashes each name in the predefined-plus-user universe once per
request; subsequent tie checks are O(1), and the full assigned-ID map is built
at most once lazily per request. Only same-tier ties involving a natural-ID
collision and at least one uncatalogued candidate are re-ranked. Fully
catalogued ties preserve the AppID-off stamp label for unstamped fallback
sessions. No dataplane catalog or wire-format change, and no live-cluster
mutation.
