# #12265 — session-hit authority fixtures and pre-verdict route writes

- **Issue**: #12265 — residual broad-suite redness in established-session authority (#11649).
- **Branch**: `fix/12265-campaign-pub`
- **Worktree**: `/var/worktrees/campaign-pub/wt-12265`
- **Base**: `af72c5a86b4841e95de88db8a320186c331cb9ef` (rebased from `83b5c955335f16d8c7835f206b210ce3ae1a5fe5`; see "Rebase onto master")

## Why

The authority tests initially did not reach established-session handling: the
WAN binding is tagged logical interface `reth0.80`, but the generated frame
and descriptor metadata omitted VLAN 80, so the descriptor dropped the packet
as unknown VLAN.

A second issue masked a real mutation: the hand-built ICMP session had an
invalid forwarding-generation stamp while the harness published `(7, 9)`. Its
first hit therefore re-resolved the route using the arriving packet's ingress
context and saved the new decision, generation stamp, and `owner_rg_id` before
the #9519 Owner/Foreign decision. The fixture made this write equal the seed.
#12074 (`fc109e12e`), merged after the original base, added a second write to
the same pre-verdict block: when the re-resolve moves the policy to-zone, it
invalidates the session's policy-revalidation stamp, so a denied foreign packet
could also force the owner's policy re-judge. A foreign hit may not revoke,
re-stamp, tear down or cache the entry (#9519). Both writes are now persisted
only after the hit is classified Owner; a foreign packet can use its
packet-local resolution for its own verdict but cannot re-stamp the session.

## What

- Fixtures (`tests_session_hit_authority_9519.rs`): TCP and ICMP WAN packets carry VLAN 80 in both the Ethernet frame and descriptor metadata (`ingress_vlan_id = 80`, `ingress_vlan_present = 1`), with frame offsets and packet length adjusted. The ICMP snapshot has the intended WAN/LAN redundancy-group ownership, LAN connected address, and static neighbors; seeded WAN egress transmits through its physical parent.
- Production: `resolve_flow_session_decision_with_conntrack` returns the stale re-resolve as `DeferredForwardingRevalidation { resolution, owner_rg_id, invalidate_policy_revalidation }` (`shared_ops.rs`) instead of writing it. The poll site (`poll_descriptor/mod.rs`) applies it right after an Owner verdict — `invalidate_policy_revalidation` when flagged, then `revalidate_forwarding_resolution` — and before the #10636 deferred close, as the inline write did, so a #9412 HA close Update still clones the refreshed route. A foreign verdict drops it with the packet. The direct `resolve_flow_session_decision` wrapper (tests and non-worker callers) has no verdict and applies it immediately.
- Tests:
  - The 10980 policy-event matrix seeds the live `(7, 9)` stamp and asserts decision, owner-RG, and stamp for every case, owner and foreign.
  - `stale_foreign_icmp_hit_does_not_mutate_forwarding_session_12265` keeps the invalid default stamp, seeds owner-RG 0, and changes the live next-hop MAC. It proves a denied foreign hit leaves decision, owner-RG, and stamp untouched, then that an Owner hit persists the new MAC, RG 1, and `(7, 9)`.
  - `owner_close_update_carries_revalidated_route_12265`: an Owner RST that is also the first hit after a FIB-generation bump publishes its #9412 close Update with the re-resolved next-hop MAC.
  - `fib_only_foreign_stale_hit_keeps_owner_policy_stamp_12265` (`tests_policy_revocation_8356.rs`): after a cross-zone FIB-only move, a foreign stale hit leaves the owner's policy stamp `Fresh`, and the owner's next hit still re-judges and revokes (#12074).
  - `established_session_re_resolves_after_fib_generation_changes_11373` (`session_glue/tests.rs`) also asserts the direct resolver persisted the re-resolved route and stamp.
- NOT changed: synced-session promotion (`promote.rs`) still writes packet-context decision, `owner_rg_id`, and `fabric_ingress` before the verdict; follow-up #12644.

## Rebase onto master

The branch was rebased from `83b5c955` onto `feb35c419`, then onto `af72c5a86` once master gained four `pkg/frr` and `docs/` commits (#12312) that leave `userspace-dp/` byte-identical. One file conflicted, `userspace-dp/src/afxdp/session_glue/mod.rs`:

- The wrapper: master's `1849c78cf` (#12257) added the trailing `None` (`prevalidated_forward_nat_match`) argument; kept, with the wrapper applying the deferred revalidation.
- The stale-route block: master's `fc109e12e` (#12074) added `sessions.invalidate_policy_revalidation(resolved_key)` before the verdict. Resolution: the struct carries `invalidate_policy_revalidation: bool`, applied before `revalidate_forwarding_resolution` at the Owner site and in the wrapper. Taking the branch side drops #12074 (its cross-zone cell fails); taking master's side does not compile; keeping the invalidation inline while deferring only the route lets a foreign stale hit flip the owner's stamp from `Fresh` to `Stale` (the new `fib_only_` test fails).

The same rebase folds review R12480 findings: the Owner persist moved above the #10636 deferred close (at `6ceb7a148` the close Update carried the stale route); the stale regression seeds owner-RG 0 (a seeded RG 1 equalled the re-resolve, so owner-RG writes were unobservable); the 10980 matrix asserts for all cases (no `if foreign` gate); `ingress_vlan_present = 1`; the direct-resolver write is pinned.

## Risk / remaining acceptance

- Owner hits still refresh route, stamp, owner-RG, and the #12074 invalidation; foreign hits use the packet-local resolution but never persist it. The direct resolver keeps writing immediately.
- Owner stale hits dropped between resolve and the verdict (`transit_destination_class_drop`, injected non-local) no longer persist the re-resolve, so the next owner hit re-resolves again. Likely a per-packet lookup cost only; not measured.
- Nothing forces a new caller of `resolve_flow_session_decision_with_conntrack` to apply `deferred_forwarding_revalidation`; one that forgets never refreshes the stamp.
- Synced-session promotion (`promote.rs`) keeps the same pre-verdict write class; follow-up #12644.
- With `--test-threads=4` on a loaded host, initial admission in the #12074 cells (and in this module) sometimes fails with `tx` 0; `origin/master` `feb35c419` shows the same signature ("the initial LiveEgress flow must transmit"), so it predates this change. Single-threaded runs are clean.
- No protocol change and no live-cluster validation.
