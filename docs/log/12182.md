# 12182 — Preserve active auth-throttle lockouts under table pressure

- **Issue**: [#12182](https://github.com/psaab/xpf/issues/12182)
- **Base**: `83b5c955` (`origin/master`)
- **Files**: `pkg/api/auth_throttle_10825.go`,
  `pkg/api/auth_throttle_12182_test.go`, `pkg/api/README.md`

## Why

The arbitrary eviction phase considered only `inFlight` and admission protection,
so a bucket with a future `lockedUntil` could be deleted before a fresh
reservation. Under a full table, this erased a victim's active lockout and its
Retry-After.

## What

Made bucket evictability depend on the injected current time and reject buckets
whose lockout is still active. Applied the same predicate to the expired sweep,
random eviction, and legacy full-table sweep. `reserve` therefore returns its
existing transient one-second refusal when all capacity is occupied by locked
buckets; no new retry policy was added. IPv6 /64 source keying is unchanged.

Added a fake-clock regression fixture that serially fills all 4096 slots with
live account/source lockouts for distinct identities. It verifies that a new
reservation is refused and a victim retains its full lockout Retry-After. A
companion case verifies expired quiet buckets still make room.

The legacy-insertion follow-up makes `recordFailure` share the guarded
room-making policy. Its bucket accessors refuse missing entries when no safe
capacity can be freed.

The new-source pressure cases directly verify source refusal; an account or
global bucket admitted after a removed guard could be evicted by a later
accessor in the same call before aggregate assertions. The coverage description
in historical commit `1e5f8b311` overstated that behavior. This fold adds
existing-source probes so a later source lookup cannot re-evict either bucket.

## Risk

Admission can now be refused transiently when the bounded table is full of live
lockouts; this preserves each active lockout and keeps the table within its
bound. Expired/unlocked buckets remain eligible for eviction. A remote client
controlling roughly 455 IPv4 addresses or IPv6 /64s can keep the table full
(about 9k failed attempts per lockout period); while it does, every identity
without existing buckets, including operators, receives 429 until the lockouts
expire. The no-auth loopback path is unaffected.
