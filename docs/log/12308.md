# #12308 — merge qualified-next-hop statements by gateway

## Why

Follow-up to #12184. Typing the qualified-next-hop (QNH) metric let the
#8436 census probe `routing-options static route xpfname qualified-next-hop`,
and it measured the site as SILENT. Two statements for one gateway compiled to
two `NextHopEntry` halves, with the interface on one and the preference or
metric on the other. Neither the strict nor the tolerant path reported it.

The halves land in different failover tiers. The interface half has no
preference of its own, so it inherits the route's 5 and joins the primary
ECMP tier. One authored floating backup therefore became an equal-cost primary
path plus an interfaceless backup, and traffic load-balanced onto the backup
instead of failing over to it.

Flat `set` produced the same split. SetPath keeps a bare
`qualified-next-hop G` leaf and a `qualified-next-hop G { … }` container as two
sibling nodes, so `set … qualified-next-hop G` followed by
`set … qualified-next-hop G preference 200` (either order) compiled a
preference-5 copy of the backup into the primary tier. For an IPv6 link-local
gateway, the bare half had no interface at all.

The first draft of this PR (`942b896d2`) added a `deepDupRules` gate instead.
The hostile review (`Review12492Opus`) blocked it:

- **B1:** merged into master, it turned #12184's
  `deepDupUnreportable` entry and `TestQualifiedNextHopCensusExemptionIsMeasured8704`
  red.
- **B2:** strict commit refused the valid bare+modifier `set` sequences above.
  Its remedy text told the operator to re-author with `set`, which is what
  they had already done.
- **B3:** routing instances, repeated `route <p>` blocks and repeated
  `routing-options` roots still split silently.
- **B4:** the subject line was 77 characters.

## What

This is a compiler fix in the #9192 shape: find-or-create on the gateway,
with a later statement overriding only the settings it authors. The
`deepDupRules` rows and `dup_qnh_12308_test.go` from the draft are removed.

- `pkg/config/compiler_static_qnh_merge_12308.go`:
  - `mergeQualifiedNextHop12308` folds each statement into the entry its
    gateway already has. Interface, preference and metric are overridden only
    when the statement authors them.
  - `finalizeQualifiedNextHops12308` closes the merge window.
- `compileStaticRoutes` (`compiler_routing.go`) sends both QNH parse paths
  through the merge: the fully-inline route keys and the child nodes. So
  does `appendStaticRouteNextHopsDeduped`, which merges same-spelling route
  blocks. That covers repeated route blocks, repeated `routing-options` roots
  and `rib inet.0 static` beside `static`. Routing instances compile through
  the same function, so they are covered too.
- `NextHopEntry.qualified` (`types_routing.go`) is an unexported, compile-only
  provenance bit. It keeps a plain `next-hop G`, which is a primary ECMP
  member, from absorbing a qualified statement for the same address.
  - `canonicalizeStaticRouteCollections` clears the bit. Every route list
    passes through it before any validator or consumer reads the routes.
  - It then re-applies the exact-duplicate fold, so a bare QNH that is
    identical to a plain next-hop still collapses into it, as before. The
    fold is deferred so that a later block can still reach the qualified
    entry.
- Census changes:
  - Deleted the #12184 `deepDupUnreportable` QNH entry.
  - Deleted the SILENT inventory row. The SILENT section is empty again, and
    its original note is restored with a #12308 paragraph.
  - Converted `TestQualifiedNextHopCensusExemptionIsMeasured8704` into
    `TestQualifiedNextHopCensusSiteConserves8704`.
- New tests:
  - `pkg/config/qnh_gateway_merge_12308_test.go`: 5 tests, 28 cells.
  - `pkg/configstore/qnh_gateway_merge_12308_test.go`: interactive `set` and
    `load set` through `CommitCheck`, 8 cells.
- `pkg/config/README.md` documents the merge.

Not changed:

- Distinct-spelling aliases (`10.5.0.1/16` vs `10.5.0.0/16`) stay independent
  sources under the #12084 effective-tier fold, and so does a bare-static IPv6
  route beside its `rib inet6.0` twin. Flat `set` gives the same result, so
  neither is a duplicate-block divergence.
- `show` and `| display set` still print both nodes. Only the compiled
  next-hop changes.

## Risk

- Compiled output changes only for routes that give one gateway two or more
  qualified statements in one route list. Those now compile to one next-hop
  in the backup tier the operator authored. Every other route compiles
  byte-identically: the merge never fires, and the deferred fold reproduces
  the old one.
- On the tolerant boot and peer-sync paths, an already-persisted split now
  installs as the merged backup instead of a primary-tier copy. That is a
  forwarding change, and the intended one.
- A peer still on an older build compiles the split until it is upgraded.
- Pre-existing and not changed here: `delete … qualified-next-hop G` removes
  only the first of the twin nodes that a bare+modifier `set` pair leaves
  (`removeMatchingNode` stops at the first match). Measured: if the bare line
  came first, the backup survives at preference 200. If the modifier line
  came first, the bare node survives and compiles at the route's preference,
  in the primary tier.
- No live cluster was modified.
