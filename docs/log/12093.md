# Issue #12093 — hierarchical interface filter leaves use last-wins

## Red before

At the PR's actual parent `83b5c9553`, repeated interface-filter leaves compiled first-wins. On the PR head, the original braced spelling `filter { input DROP; input ACCEPT; }` had been fixed, but compact `filter input DROP; filter input ACCEPT;`, repeated `filter {}` siblings, and mixed spellings still compiled first-wins: the compiler only read the first `filter` sibling. The review also found that `scalar: true` rejected `filter { input { f1; } }` at `CommitCheck`, although the #10293 contract accepts this single-child spelling through `CompileConfig`.

## Change

- Kept the fixed-arity scalar gate on inet/inet6 `filter input` and `filter output`, with a scoped exception for exactly one child token in the block-form spelling `input { f1; }` / `output { f1; }`. Multi-value spellings remain rejected.
- Changed the inet and inet6 compiler reads to visit every `filter` sibling and each matching input/output leaf in authored order, so compact, repeated-block, and mixed sibling spellings resolve last-wins.
- Added production `LoadOverride` + `CommitCheck` regressions for compact repeats, repeated blocks, and both mixed orders across inet/inet6 and input/output, plus the #10293 single-child block spelling. The existing `CompileConfig` and scalar-arity regressions remain.
- Reused the existing #6774 `blockValue` opt-in and `singleBlockValue()` helper for the scoped scalar exception; removed the unverified claim that Junos emits the interface-filter block spelling.
- Added strict `CommitCheck` rejection cases for an empty filter value, a filter value with a sub-statement, and the same block form on `description`; each case is tied to its guard-specific error and was checked by reverting that guard.

## Residual / risk

- No live-cluster mutation or traffic validation was performed. Project-wide validation remains with the main agent; the broader package-test failures above are reported rather than silently omitted.
- Upgrade impact for repeated and split filter siblings, including the `lo0` control-plane filter, is recorded below for #12511. The unchanged family-sampling first-sibling reader is tracked separately in #12512; the editor/compiler mismatch remains tracked in open issue #12508.
- Under the CURRENT last-wins compiler behavior (without choosing the #12508 editor/compiler contract), pre-#12093 compiles read only the FIRST `filter` sibling per unit/family and the first matching leaf inside it: `FindChild("filter")` followed by `FindChild("input"/"output")` (`058b3a75a:pkg/config/compiler_interfaces.go:682-687` inet, `:748-753` inet6). Current compiles visit every `filter` sibling and matching input/output leaf in authored order, overwriting the unit value (`pkg/config/compiler_interfaces.go:682-691` inet, `:750-757` inet6). The effective binding changes only when this selects a different reference, including absent→name or `PROTECT`→empty; identical references do not change the binding, and packet outcomes depend on the referenced filters' contents.
- Persisted-store probes (old `058b3a75a` `Store.LoadOverride` + `Commit`, then head `Store.Load`) reproduced these cases: (a) repeated leaves inside the first sibling change first→last (`filter { input FIRST4; input LAST4; }`: lo0 inet `FIRST4→LAST4`); the same-direction cross-sibling repeat `filter { input A; } filter { input B; }` changes `A→B`. (b) A direction present only in a later sibling changes none→last, even when that binding is not repeated (lo0 inet/inet6 input `""→PROTECT4/PROTECT6`; ge-0/0/0.0 output `""→OUT`); the compact split-sibling spelling `filter input X; filter output Y;` also leaves ge output dormant on the old compiler (`X/""`) and binds it on head (`X/Y`). (c) A later `input "";` unbinds an earlier lo0 `PROTECT4`: old boot keeps `PROTECT4`, head `Store.Load` yields `""`; fresh head `LoadOverride` + `Commit` also accepts the empty binding with no warnings. The #12093 guard rejects only the block spelling `filter { input { ""; } }` with `unexpected trailing token ""` (`pkg/configstore/interface_filter_repeated_12093_test.go:87-101`); leaf `input "";` passes `CommitCheck` + `Commit` with zero warnings. Open #12508 notes empty filter names commit and unbind. With both lo0 families empty, `applyLo0Filter` deletes the kernel nft table (`pkg/daemon/daemon_nft.go:151-157`); the live userspace backend maps an empty lo0 name to `Ok(None)` (`userspace-dp/src/filter/compiler.rs:452-453`), and the legacy eBPF path skips empty lo0 names (`pkg/dataplane/compiler_filter.go:377-392`; `ebpf` is marked legacy at `pkg/config/types_system.go:38`), silently removing host-bound filtering.
- The lo0 path is code, not just a comment: `compileInterfaces` visits each interface child without a name-specific exclusion (`pkg/config/compiler_interfaces.go:67-82`), `resolveDerivedConfig` looks up `cfg.Interfaces.Interfaces["lo0"]` at line 104 and hoists unit-0 inputs to `System.Lo0FilterInputV4/V6` at `pkg/config/compiler_derivations.go:103-107`. Those names reach the kernel lo0 hook (`applyLo0Filter`, `pkg/daemon/daemon_nft.go:144-150`), userspace snapshot (`pkg/dataplane/userspace/flow.go:91-92` → `pkg/dataplane/userspace/protocol.go:1040-1041` → `userspace-dp/src/afxdp/forwarding_build/mod.rs:880-881`), and eBPF compiler (`pkg/dataplane/compiler_filter.go:377-392`).
- Both compiler-loop halves have separate regressions: `TestInterfaceFilterScalarDuplicatesLastWins12093` (`pkg/config/interface_filter_scalar_12093_test.go:9`) catches repeated leaves inside a sibling (restoring first-leaf reads made all 4 cases fail with DROP, want ACCEPT); `TestLoadOverrideCommitCheckFilterBindingsLastWins12093` (`pkg/configstore/interface_filter_repeated_12093_test.go:11`) catches repeated `filter` siblings (restoring a single `FindChild("filter")` failed with effective A, want B, while the scalar test remained green).
- Remediation: Before upgrading, on every HA peer and before any node runs the new compiler, consolidate each unit/family's bindings into ONE hierarchical `filter { input X; output Y; }` block. Verify with hierarchical show (`Store.ShowActivePath`, `pkg/configstore/store_format.go:39`). In the probe, old `display-set` (`Store.ShowActivePathSet`, `pkg/configstore/store_format.go:132` at `058b3a75a`, line 143 on head) printed the dormant lo0 PROTECT4 binding while the old compiled `Lo0FilterInputV4` was empty; display-set cannot show which sibling the old compiler enforced. Open #12508 means `set`/`delete`/`deactivate` can still edit the first filter block while the compiler reads the last, so CLI edits do not guarantee consolidation: inspect hierarchical output and explicitly fold the bindings into one block. Otherwise, during a mixed-version HA rollout old and new peers enforce different filters, so failover can change or remove the active filter.
