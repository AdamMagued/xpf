# #12186 — union equivalent OSPF area interface fragments

- **Timestamp**: 2026-10-11 (PR branch base `83b5c9553`). The earlier note
  named `a714c90d4`; the OSPF renderer, validator and reuse-test files are
  byte-identical between those bases, so the original RED reproduction
  remains applicable.
- **Action**: emit one FRR interface block per resolved interface and
  equivalent area; union disjoint settings (including same-area aliases) and
  reject conflicting settings at strict compile.

## Red before

Strict compile accepted the cost and MD5 fragments under area IDs `0` and
`0.0.0.0`. A firsthand `buildManagedSection` repro on PR head `2bf3ca0d`
rendered cost 10 without authentication; base `83b5c9553` emitted both in
duplicate interface contexts. FRR 10.7.1 `frr-reload.py --test` showed the
base `Lines To Add` included both cost and MD5 auth lines, while the head
included only cost. The same loss reproduced for same-area authored aliases
`ge-0/0/1.0`, `ge-0-0-1.0`, `ge-0/0/1`, and `ge-0-0-1`, all resolved to
`ge-0-0-1`.

The cross-area p2p repro used the lenient path: the renderer dropped the
later area fragment, but `generateInterfaceSettings` still counted its
explicit network type, suppressing the generated line. `frr-reload.py
--test` had no `ip ospf network point-to-point` line before the recount.

## Change

- OSPFv2 and OSPFv3 union disjoint settings from equivalent-area fragments
  into one interface context, including authored aliases resolving to one
  Linux device. Strict compilation rejects conflicts; tolerant input retains
  the first present scalar value and warns.
- OSPFv2 MD5 key IDs union by ID for rollover. Passive state remains unioned,
  and network-type suppression now considers only fragments surviving the
  same first-area rule as the protocol renderer.
- Interface activation retains the first fragment's original area spelling,
  so spelling and tolerant conflict precedence remain order-sensitive. The
  README documents the renderer contract and alias scope.
