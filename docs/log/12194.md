# Issue #12194 — Guard VLAN-alias binding indices

## Why

On base `a78c217fc5a94b2f7d74124588f205b7a0086cb3`, `applyAliasBindingRowsLocked` multiplied an alias child's ifindex by the binding stride before checking the ifindex bound. Since the composed index is `uint32`, child ifindex `268435473` with queue 0 wrapped to index 272 (ifindex 17, queue 0), passed the post-multiply dense-cap check, and overwrote that primary row with the parent's slot.

## What

The alias apply loop uses the shared `bindingIfindexInRange` pre-multiply bound; the watchdog alias decision now uses that same helper instead of a separate unsigned cap check. The helper rejects child 0 in both decisions; alias collection also filters nonpositive snapshot ifindices before apply. Apply fails closed before index composition; the existing queue and post-multiply cap checks remain unchanged.

Added fake-map regressions for the `268435473` overwrite/fail-closed case and the exact `2^28` slot-zero map case. The valid ordinary-alias/ctrl-untouched control is covered by the existing #7497 test; its duplicate #12194 cell was removed. The slot-zero cell is explicitly map-only: `userspace-xdp/src/binding_index.rs` uses `checked_mul` for packet-side lookup and returns `None` for this high ifindex, so the cell makes no packet-steering claim.

## Risk

The watchdog alias-repair path is already guarded by #12307 (`619660468`, `watchdogAliasBindingIndex`); wrapped child indices are rejected before repair. In `statusLoop`, apply runs before `verifyBindingsMapLocked` while `Manager.mu` is held, and both consume the same snapshot/status; an apply failure skips the watchdog, which is the separability boundary. A real alias child ifindex outside `MaxInterfaces` remains fail-closed and disables userspace ctrl. Supporting real ifindices above the configured cap requires coordinated map-capacity changes; at or above `2^28`, raising the cap alone is insufficient because the uint32 stride product still wraps and a wider-index design is needed. The two full-suite failures reproduce on base `4a17e0d29` and the fold tree; they are not attributed to this change.
