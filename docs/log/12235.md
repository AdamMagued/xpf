# Issue #12235 — keep deferred startup snapshots pending until publication

## Why

A successful userspace apply can defer its full snapshot while XSK startup is unresolved. Treating that return as converged stamped the active digest, advanced HA config high-water/ACK, and advertised takeover readiness before the helper enforced the generation. In-band helper refusal on the deferred status-loop publish was not connected to the HA config apply result.

## What

Applied markers remain invalidated until a synchronous or status-loop publish
lands. Deferred configs retain their digest and an HA completion channel; the
userspace manager reports in-band refusal to the daemon, and a pending full
snapshot blocks takeover readiness with its generation in the reason. A failed
apply tail retires its pending HA completion with that failure instead of
acknowledging partial convergence. The applied marker is not yet protected end
to end: master's #12072 catch-up can still stamp a debt-bearing deferred apply
whose tail failed once it publishes (follow-up #12641).

A publication callback at a monotonically newer helper generation settles the
deferred record, but stamps it applied only while its config is still the
active target. A newer generation proves only that some snapshot landed, so a
different config promoted in the meantime supersedes the record (HA NACK) even
when that config's own apply tail failed. Like every other marker site, the
stamp also requires that no invalidation debt remains: a scan-failure debt kept
after publication withholds the marker, keeping the #4957 config-sync shortcut
off until a later complete discharge clears it. A later successful synchronous
apply settles the record from its own tail: superseded for a different config,
applied for the same config unless invalidation debt is still owed. A refused
record is re-armed on a same-config re-push, and the deferred-MAC replay
refreshes its generation. The ordered HA apply consumer bounds its completion
wait by the configured apply grace and NACKs on timeout. It re-checks the peer
boot incarnation after waiting so an old payload cannot advance high-water or
receive an ACK after a peer reboot. Deferred syncs are logged at Info and still
report config-sync divergence.

## Risk

HA config sync remains fenced while a deferred snapshot is pending, up to the
configured grace; helper refusal or timeout NACKs and allows the sender's
existing retry cadence to re-send the generation. On an RG0 secondary the store
rejects local commits, so only a commit-confirmed timeout revert can promote a
different config while a peer config waits; the active-target check covers that
narrow case. A deferred landing that keeps scan-failure debt leaves the applied
marker withheld, so the peer's next re-push re-enters the apply instead of
taking the converged shortcut. The failed-tail catch-up stamp is pre-existing
master behavior tracked by #12641. The session-invalidation behavior tracked
separately by #12073 was not expanded here.
