# Issue #12196 — reject non-executable userspace helper candidates

## Why

`findBinary` accepted implicit working-directory/build-tree/argv0-relative candidates on `os.Stat` success alone. A stale 0644 file or directory therefore shadowed a usable executable on `PATH`; helper startup then failed instead of trying the valid candidate. Explicitly configured paths also accepted non-executable files without an actionable diagnostic.

## What

Implicit candidates are skipped if they are directories or fail the effective-access check used by `exec.LookPath`, including on noexec mounts. When effective-access checks are unavailable or blocked, the check falls back to execute permission bits. Skipped candidates and their reasons are appended to the final not-found error. Explicit paths remain strict: missing paths retain the not-found error, while directories and non-executable files return informative errors and never fall back to `PATH`. Candidate order and the existing PATH fallback are unchanged.

## Risk / residual

The check still precedes process start, leaving a time-of-check/time-of-use gap; malformed executable-bit files can also fail at start. If the version-pinned argv0-relative helper is unusable, unchanged `PATH` fallback can still resolve a helper from `versions/current`; normal upgrades stop xpfd before flipping `current`. No live cluster was mutated.
