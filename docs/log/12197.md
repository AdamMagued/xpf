## Change

`test-failover.sh` records the failback observation timestamp when its bounded polls see fw0 primary for the requested RG0/RG2 moves. The earlier RG1 failback slice is not represented by this anchor. The observation can lag the actual role change: status polling is one-second-granularity, and command/check latency adds delay; because RG2 is polled after RG0, its observation can trail the actual move by up to `MANUAL_FAILOVER_DEADLINE` (10s) plus command/check time. A completed client before manual failback is VOID because it cannot witness that event.

`iperf3_sum_parse.py` accepts optional `--failback-at` and applies the established-stream recovery check at that event as well as the crash. A failback with no per-stream interval starting at or after the recovery window opens is VOID because there is no post-event evidence; an observed stream loss with telemetry is FAIL. The default whole-run per-stream zero-interval budget (`MAX_STREAM_ZERO_INTERVALS=0`) already catches persistent stream loss, so this event-specific oracle adds defense-in-depth and failure attribution rather than replacing that gate. `iperf-throughput-selftest.sh` checks both early-completion cells independently (exactly two VOID cells and no early-completion PASS), along with the event arguments and timestamp capture.

## RED then GREEN evidence

The committed synthetic shape exercises the failback-specific stream attribution: the crash-only stream oracle and aggregate interval check remain green, while the second event check reports the streams that did not resume. On the PR base, the default whole-run per-stream zero-interval gate also rejects persistent loss; the event oracle provides a targeted failback verdict.

```text
PASS longest outage was 2 consecutive low-throughput intervals (budget 2)
PASS all 8 pre-failover streams (5, 6, 7, 8, 9, 10, 11, 12) resumed data within 3s
FAIL streams 6, 7, 8, 9, 10, 11, 12 carried data before failback but did not resume within 3s
```

A client log ending before the failback recovery window has a VOID verdict. The boundary test distinguishes a log ending at 21s (no per-stream interval starts at or after 21s; VOID) from one ending at 22s (a positive 21–22s interval is present and permits PASS).

A client log ending at 31s with failback at 60s emitted `VOID client telemetry ends at 31.00s, before the failback event at 60s: no failback stream evidence`.
