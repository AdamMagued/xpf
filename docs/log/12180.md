# Issue #12180 — gRPC cursor session scans honor cancellation

## Why

A selective `GetSessions` cursor filter that did not fill a page could scan the full v4 and v6 tables after the request was cancelled. Page-full filtered totals then scanned both families without sampling cancellation, while unfiltered totals called `SessionCount`, an uncancellable full v4+v6 map walk. These walks could hold a shared session-walk slot through EOF after cancellation; unfiltered callers only got gRPC cancellation after `SessionCount` finished.

## What

- Added sampled context cancellation checks to v4/v6 cursor callbacks and count-only total iterators, with direct checks at phase boundaries. Cancellation stops the current sampled walk, prevents starting the next family or total pass, and returns the gRPC `Canceled` status.
- Routed filtered and unfiltered cursor totals through the same cancellable iterator path instead of using uncancellable `SessionCount`. The count excludes reverse entries, never publishes a partial result, and releases the shared slot on cancellation.
- Added seven v4/v6 cursor, filtered-total, page-full filtered-total, and unfiltered-total cancellation regressions. They verify early stopping, expected family boundaries, `Canceled`, and slot release; count-walk cases pin the 1,024-row sampling bound.

## Risk / residual

An unexpectedly absent session map now surfaces the iterator error for unfiltered cursor totals instead of `SessionCount`'s previous zero. Cancellation tests use a deterministic synthetic dataplane: total walks cancel at row 512 of 20,480 and assert stopping within 1,024 visits; tests verify family boundaries and slot release. No live dataplane or cluster was exercised.
