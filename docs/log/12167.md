# #12167 — fail closed on backward-clock confirm recovery

- **Issue**: #12167 — standalone commit-confirmed recovery could re-arm an unbounded timer after a backward wall-clock step.
- **PR**: #12382.
- **Parent**: `a78c217fc` (#12186); the PR head is on `fix/12167-campaign-pub`.
- **Worktree**: `/var/worktrees/campaign-pub/wt-12167`.

## Why

`recoverPendingConfirmLocked` computed the recovered timer as `Deadline - current wall time`. If reboot recovery ran with the clock before persisted `ArmedAt`, a 10-minute window with the wall clock 30 days behind could re-arm for 720h10m. `time.AfterFunc` then counts down monotonically; a later wall-clock correction does not shorten that timer. Since elapsed downtime is unknowable after this clock step, recovery rolls back instead of trusting the wall-clock-derived remaining duration.

## What

- Treat a current wall clock before a non-zero persisted `ArmedAt` as conclusive backward-step evidence and use the existing fail-closed boot rollback path, including a specific warning and journal reason.
- Bound a recovered timer to the lesser of `Deadline - now` and the duration represented by `Deadline - ArmedAt`; cap legacy records without `ArmedAt` at `MaxCommitConfirmedMinutes`.
- Before a FIRST rollback's active write, durably rewrite `confirm.json` with a past deadline sentinel. If marker publication is interrupted, the retained record then reconstructs teardown debt even after clock correction or an alarm-triggered rollback. If the sentinel write fails, recovery still rolls back in memory, marks persistence degraded and teardown owed, and retries the sentinel before the active rollback write; it never returns with the unconfirmed FIRST config active and no timer. A crash after the sentinel but before the active write replays the rollback on next boot; the journal may report the ordinary #4577 expiry reason, which is cosmetic.
- Preserve normal remaining-time re-arm and the active daemon clock-skew alarm behavior. Document the policy and its inability to reconstruct downtime.

## Risk / residual

A reboot with a wall clock before `ArmedAt` immediately reverts the pending commit-confirmed change; this can be earlier than the intended timeout when boot time is untrusted, but avoids extending an unconfirmed configuration by unknowable downtime. Legacy records without `ArmedAt` cannot recover their exact original duration; their recovered timer is bounded by the API's 65,535-minute maximum. No monotonic deadline is persisted across reboot. If FIRST sentinel persistence fails, the rollback target is installed in memory, teardown remains owed and persistence health degrades; the active marker stays unchanged until retry durably writes the sentinel and then the active rollback marker.
