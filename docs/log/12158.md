# #12158: packaged xpfd dirty marker

## Scope after #12357

#12158 reported two defects:

- Both `bake.py` and the Makefile decided dirtiness with `git diff --quiet`,
  which misses staged edits and untracked inputs.
- `bind_deb_identity` stripped xpfd's `-dirty` suffix before comparing it, so
  a binary built from source other than HEAD could be signed as HEAD.

#12357 (`ff1a29c66`, which closes #12141) fixed the first defect. It added the
shared `scripts/image/build_provenance.py` probe and records `source_dirty` in
the signed manifest. That probe stays the only dirtiness test, and dirty
packages stay bakeable. Both are the parent's policy decision for this PR. This
branch fixes the second defect on top of #12357.

### History

The first version of PR #12506 (`24f93a61d` and `2349975e9`, on base
`a11e59eac`) added its own `git status` check, which excluded
`debian/changelog`, and refused every `.dirty` package. It conflicted with
#12357 in the same lines. The Opus review of #12506 (B1/B2) found that no
mechanical conflict resolution worked, so the branch was rebuilt on master
`da3dd7b32`.

## Why

`make deb` rewrites the top line of `debian/changelog` and then runs
`dpkg-buildpackage`. That reruns the Makefile through `debian/rules`
(`$(MAKE) build build-ctl build-userspace-dp`).

The inner make evaluated `VERSION ?= $(shell git describe --tags --always
--dirty)` after the rewrite. Every packaged xpfd therefore reported `-dirty`.
For example, the clean-labelled `xpf_0.0.19737+gbc658a5bdd66` reports
`working-17329-gbc658a5bd-dirty`.

`bind_deb_identity` stripped that suffix to cope, which also erased a real
marker. A package labelled clean whose xpfd was built from dirty source still
bound as that commit. Under `--skip-build`, if the package's commit was not in
the local repository, no version comparison ran at all.

## What

- **`Makefile` (`deb` recipe):** before rewriting the changelog, read
  `DEB_VERSION` once and use that value for both the changelog and the binary.
  - `xpfd_version` is HEAD's `git describe --tags --always`, plus `-dirty`
    exactly when that value ends in `.dirty`.
  - `dpkg-buildpackage` runs with `VERSION=$xpfd_version`. The inner `VERSION
    ?=` keeps the environment value.
  - An explicit `VERSION`, on the command line or in the environment, keeps
    make's normal precedence. The recipe echoes the value it passes.
- **`scripts/image/bake.py` (`bind_deb_identity`):**
  - Requires an xpfd `-dirty` marker if and only if the package version ends
    in `.dirty`, checked before the commit is resolved.
  - The check applies to normal and `--skip-build` bakes, including when the
    commit object is absent.
  - `-dirty` is stripped for the `git describe` comparison only after that
    check.
  - Dirty packages whose markers agree still bind.
  - Neither refusal message claims to be about signing, because both refusals
    also stop unsigned bakes (review F3).
- **`docs/install-images.md`:** the identity paragraph now states the marker
  rule and says that older clean-labelled packages must be rebuilt.
- **No `debian/changelog` exclusion (review F1):**
  - `DEB_VERSION` is read before the rewrite.
  - The probe counts any tracked changelog edit as dirty, and a test cell pins
    this. The changelog ships as `/usr/share/doc/xpf/changelog.gz`.
- **NOT changed:**
  - `build_provenance.py`
  - the manifest `source_dirty` field
  - `deb_version_for_head`
  - plain `make build`, which still uses `git describe --dirty` (tracked files
    only)
  - `test/incus/deploy-lib.sh`, which records `git describe --dirty` but
    compares nothing.

## Mechanism check

This check came first, to confirm the variable survives `debian/rules`.

A scratch debhelper-compat 13 package mirrored our rules: `dh $@` and
`override_dh_auto_build: $(MAKE) build`. Its Makefile used `VERSION ?=
$(shell echo inner-describe-dirty)` and `LDFLAGS := -X main.version=$(VERSION)`.

- `VERSION=outer-describe dpkg-buildpackage -us -uc -b --no-sign` linked
  `-X main.version=outer-describe`, and `$(origin VERSION)` was `environment`.
- Without the variable, the inner default was used.

GNU make 4.4.1 expands every recipe line before it runs the first one. Two
`$(shell date +%s%N)` expansions on either side of a `sleep 1` differed by
1.6 ms. So every `$(DEB_VERSION)` in the recipe reads the tree before the
rewrite.

## Risk

- **Compatibility break (F4).** Every clean-labelled package built before this
  change has `-dirty` in its xpfd version. Bake refuses such a package,
  including under `--skip-build`, until it is rebuilt with `make deb`. Old
  `.dirty` packages still bind.
- **Operator-visible version change.** Clean packaged builds now report
  `xpfd version` without `-dirty`. First-install seeding also names
  `/var/lib/xpf/versions/<v>` without it, so a same-commit rebuild of an old
  package lands in a new directory. `postinst_status` compares versions with
  Debian ordering, which rejects `working-*` strings with or without the
  suffix (an upstream version must start with a digit), so its behavior is
  unchanged.
- **Explicit `VERSION` override.** The override is embedded as given. Bake
  refuses a resulting mismatch. `make dist-repo` and the cluster dogfood
  deploy do not check it, which is unchanged from master.
- **Repeated probe runs.** Each `$(DEB_VERSION)` expansion is still a separate
  probe run, as before this change. The changelog and the embedded marker now
  come from one run. Bake's agreement check is the backstop if the tree changes
  while make expands the recipe.
- **Detection timing.** A mismatch produced by the build itself can only be
  found after `make deb`, because the check reads the built xpfd. No refusal
  remains that could have been made before the build (F3).
