# Issue #12184 — validate the qualified-next-hop metric

## Why

The qualified-next-hop `metric` leaf was untyped, unlike its sibling `preference`. Strict schema validation therefore let `-1`, `4294967296`, and non-numeric values such as `abc` reach compiler paths that ignore unparsable integers or treat out-of-u32 values as tier 0. That silently erased the authored failover order and omitted invalid FRR metric exports.

## What

- Typed the metric leaf as an integer in `0..4294967295`, matching the userspace tier and FRR export consumers. Zero is the primary metric tier and is explicitly valid; the u32 ceiling is the consumer boundary. This intentionally differs from preference's `1..254` range.
- Made strict schema walking use the existing #9235 QNH flat-run expansion for `qualified-next-hop` children, matching the compiler's view so the metric validator also covers modifier chains.
- This also accepts 11 QNH spelling classes that the prior strict gate refused: flat preference-first; three braced fused-child runs; four packed multi-modifier runs; two route-packed runs; and the routing-instance braced form. The compiler already consumes the authored values. Tests pin F05/F06 metric-first chains plus braced fused-child and packed multi-modifier accept-and-compile cases.

## Risk / residual

- The strict gate's 11-class spelling expansion is an intentional compatibility change, not only a range tightening. The metric remains constrained to `0..4294967295`; accept-and-compile cells pin representative braced fused-child and packed multi-modifier forms. Repeated hierarchical qualified-next-hop blocks still compile into separate entries rather than merging modifiers as flat `set` does; #12308 tracks this divergence. The measured #8704 exception avoids claiming either setting was dropped: both survive on separate `NextHopEntry` objects, while the census detects a shape difference. No generic duplicate report or strict rejection is added. No live cluster or hardware was mutated.
