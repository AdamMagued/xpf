# #12539 — mgmt-VRF ECMP static with realm stamp fails RouteReplace

- **Timestamp**: 2026-10-10 (ownership fold 2026-10-12)
- **Action**: Single-path mgmt statics keep `RTPROT_STATIC` plus the xpf realm.
  ECMP (multipath) mgmt statics carry no realm; they are owned through the
  dedicated rtm_protocol `config.ManagementVRFMultipathStaticProtocol` (0x58).
  The reconcile reaps either marker and never deletes a (destination, priority)
  slot it has just replaced.
- **Base**: `origin/master` `948761f80` (rebased from `f9cb48ed8`)
- **Files**: `pkg/config/routinginstance_reserved_name_9622.go`,
  `pkg/daemon/mgmtvrf_static_routes.go`, `pkg/daemon/mgmtvrf_routes.go`,
  `pkg/daemon/daemon_flow.go`, `pkg/routing/routes.go`,
  `pkg/daemon/mgmtvrf_static_ecmp_12539_test.go`,
  `pkg/daemon/mgmtvrf_static_ecmp_kernel_12539_test.go`,
  `pkg/routing/rtproto_test.go`, `pkg/daemon/README.md`, `pkg/dhcp/README.md`,
  `docs/critical-patterns.md`, `docs/log/12539.md`
- **Parent**: #12084 (GLM second-model residual on PR #12332, reproduced firsthand)

## Why

Kernel contract (7.2.8, `fib_get_nhs`): a top-level `RTA_FLOW` on a multipath
route must equal the first leg's per-nexthop `RTA_FLOW`, otherwise the add
fails with "Nexthop class id does not match RTA_FLOW". vishvananda/netlink
v1.3.1 `NexthopInfo` has no flow field, so the library can neither emit nor
parse a per-leg `RTA_FLOW`. `mgmtStaticRoutesDesired` stamped Realm 0x585046 on
every desired route, so every ECMP mgmt static failed RouteReplace with EINVAL.

Dropping the realm from ECMP routes (first commit) installs them, but leaves
them unowned. Cleanup reaps only marked routes, and `NLM_F_REPLACE` overwrites
only the same (destination, priority) slot. Removing the static, or changing
its destination or preference, therefore left an orphan that kept forwarding.
The commit still succeeded. On 7.2.8, prio 5 -> 7 kept both routes with 5
preferred. A /24 -> /16 change kept the /24, which shadowed the /16.

## What

Marker options, each probed on 7.2.8 in a private netns with the repo's
netlink library:

- **Per-leg `RTA_FLOW`**: the kernel accepts it (`ip route ... nexthop ...
  realms`), and `ip -d route` shows it, but the library dump reports realm 0.
  It would need raw-netlink install and dump paths. IPv6 stores no
  `RTA_FLOW`, so IPv6 ECMP would stay unowned.
- **In-memory ECMP set + startup adoption**: puts no marker on the route. After
  a restart across a config change, such as a crash between commit and
  reconcile or a boot-time rollback, its orphans look like operator ECMP routes.
- **Dedicated rtm_protocol (chosen)**: it lives in the fixed rtmsg header and
  round-trips through the library in both families. The kernel delete match
  compares it (`fib_table_delete`, `ip6_route_del`), so a stale xpf delete
  returns ESRCH against an operator `RTPROT_STATIC` ECMP route at the same slot
  (probed, both families).

Changes:

- `config.ManagementVRFMultipathStaticProtocol` = 0x58 ('X'). It is unassigned
  in the kernel UAPI, iproute2 `rt_protos`, and FRR `rt_protos.d`.
- `mgmtStaticRoutesDesired`: multipath routes use 0x58 and realm 0.
  Single-path routes are unchanged, including the backup-router
  (`RTPROT_STATIC` + realm).
- `mgmtStaticRouteOwned`: protocol 0x58, or `RTPROT_STATIC` + realm. The present
  check accepts both protocols. An operator-identical `RTPROT_STATIC` route
  still satisfies a desired key and is never claimed.
- Replaced-slot rule: a successful replace records its (family, destination,
  priority) slot. Cleanup never deletes an owned snapshot route in that slot,
  because `NLM_F_REPLACE` already overwrote it and the kernel matches deletes
  leniently. A single-path delete matches the first leg only. A multipath
  delete matches leg by leg over the installed legs only. IPv6 deletes every
  matching leg. Probe: with one shared marker, single -> ECMP, ECMP -> single,
  and 3 -> 2 legs each deleted the replacement on IPv4. On IPv6, single -> ECMP
  removed a leg, and ECMP -> single and 3 -> 2 deleted the route while returning
  ESRCH, which the reconcile tolerates. This also pins the single -> ECMP
  invariant: the stale single-path delete is no longer issued, so the
  realm-mismatch ESRCH no longer protects the new route.
- DHCP precedence: `mgmtVRFRouteInventory` counts 0x58 routes as operator
  authority alongside `RTPROT_STATIC` (#9943). An ECMP static default
  therefore still suppresses the DHCP default instead of being ignored with a
  SECURITY "non-static" warning.
- `rtProtoName`: 0x58 renders as `static` in `show route`.
- The ownership comment above `mgmtStaticRouteRealm` (formerly "This realm tags
  only routes reconciled by xpf") now describes both markers and the precise
  kernel/library contract.

## Known gaps (pre-existing or bounded)

- IPv6 single-path mgmt statics are still never reaped, because the kernel
  stores no `RTA_FLOW` for IPv6. This is unchanged.
- Earlier builds installed IPv6 ECMP mgmt statics as `RTPROT_STATIC` with
  realm 0. An identical desired route is present and not claimed. A removed
  one stays, as before.
- systemd-networkd v262 (`ManageForeignRoutes=yes` default): on any link
  (re)configure, `link_drop_unmanaged_routes` drops foreign IPv4 multipath
  routes, because they have no assigned link. `KeepConfiguration=static`
  (RETH, VLAN parents) keeps only `RTPROT_STATIC`. A 0x58 ECMP route is
  therefore also dropped by a reconfigure of such a link, where a realm-0
  `RTPROT_STATIC` route would survive. Other links drop both. The
  post-networkd management reconcile reinstalls the route, as it does every
  dropped table-999 route.
- Multi-alias edge: the slot rule assumes one route per slot. xpf never appends
  a route; only an operator `ip route append` into an xpf slot breaks that.

## Validation

- Kernel probe (7.2.8, private netns, vishvananda/netlink v1.3.1):
  - Multipath + top-level realm: EINVAL.
  - Top-level realm with leg 0 unstamped (iproute2): "Nexthop class id does not
    match RTA_FLOW".
  - Per-leg realms: install works, but the library reads realm 0.
  - 0x58 multipath: round-trips in both families.
  - Same-marker stale deletes: self-delete as listed above.
  - Cross-marker stale deletes (`RTPROT_STATIC`+realm <-> 0x58): ESRCH, intact.
  - Prio-change stale delete: removes only the old slot.
- `TestMgmtStaticECMPLifecycleInKernel12539` (root-gated, SKIPs without
  CAP_NET_ADMIN). It runs IPv4 and IPv6 with 2+ gateways through these steps:
  single -> 3-leg ECMP -> 2 legs -> preference 7 -> wider destination ->
  single -> ECMP -> removed. It asserts the exact table-999 state each step,
  with operator ECMP routes untouched, and that re-applying the same config
  issues no replace or delete (kernel read-back matches the desired key). PASS
  as root.
- `TestMgmtStaticECMPReconcileReapsStaleRoutes12539` (fake) covers preference,
  destination, removal, replaced-slot, operator, and legacy cases, plus a
  steady-state no-churn pass.
- `TestMgmtVRFECMPStaticDefaultSuppressesDHCPDefault12539` checks that an ECMP
  static default suppresses the DHCP default.
- `TestMgmtStaticRoutesDesiredECMPOwnershipMarker12539` checks the markers.
- `TestRtProtoName/xpf-mgmt-ecmp-static` checks the display name.
- RED mutants:
  - Slot rule removed: the fake replacement is deleted, and the kernel test
    loses both families' ECMP at step 3.
  - ECMP stamped `RTPROT_STATIC`: four 12539 cells fail.
  - 0x58 not owned: prio-5 orphans at kernel step 4 in both families; fake
    orphans.
  - Classifier reverted: the DHCP default is installed.
  - Present check `RTPROT_STATIC`-only: steady-state churn.
- GREEN: the 12539/11449/12084/11792/9943/5867/5108/11450/11424 cells as user
  (kernel cells SKIP) and as root (kernel cells run); full `pkg/daemon` and
  `pkg/routing` suites. gofmt and vet are clean.

## Risk

- Single-path routes and the backup-router are byte-identical to master.
- ECMP routes, which never installed on IPv4 before, now carry protocol 0x58.
  They show as `proto 88` in `ip route`, and as `static` in xpf `show route`.
- The networkd bound above is the only new exposure. The full apply's
  post-networkd reconcile covers it.
- No live cluster was mutated.
