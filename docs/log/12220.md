# Issue #12220 — diagnose predefined application shadows

## Why

A user `application-set junos-http` shadows the predefined `junos-http`
application through two resolution paths: direct policy references resolve
application-first to predefined tcp/80, while nested set members resolve
user-set-first to the set's tcp/8443 member. A term-based user
`application junos-http` also mints an implicit application-set under that name,
so direct references resolve to predefined tcp/80 while nested members expand
the authored term. The strict collision gate diagnosed the authored-set spelling
but missed the term-based spelling, leaving one token with different enforced
meanings by reference path.

## What

The application-name AST gate rejects both authored application-sets and
term-based applications whose implicit sets shadow predefined application
names: strict commit rejects, while lenient load warns and records the colliding
name so direct and nested policy references are refused rather than using an
arbitrary winner. A SIMPLE (non-term) user application shadow of a predefined
application remains allowed. Added strict/lenient regression coverage for both
spellings, userspace snapshot quarantine rows, and a duplicate-warning pin; the
gate documentation describes the distinction.

## Risk / residual

Strict commits now reject authored application-sets and term-based applications
that shadow predefined applications. Lenient loads warn and quarantine affected
references; userspace refuses the whole policy snapshot, preserving previous-
good state or booting default-deny. No live-cluster mutation or validation was
performed.
