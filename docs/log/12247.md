# 12247 — use the main-plus-node zone-name union for tolerant zone quarantine

- **Issue:** #12247 — tolerant quarantine must use the same main-plus-node zone-name union as strict collision validation.
- **Base:** `a097ef0dd66adb210d8635c868f051099bc89fa8` (rebased from `51ace11d0` for the PR #12462 confirm fold, and earlier from `a714c90d4` for the R1 fold)
- **Branch:** `fix/12247-campaign-pub` (PR #12462)

## Why

Strict zone-ID collision validation sees the main configuration and both node views, but tolerant quarantine previously recomputed the collision set from each node snapshot independently. When a colliding name existed only in the peer node's view, the other snapshot could retain a conflicting zone rather than applying the same deterministic survivor decision.

## What changed

- Record the sorted main/node0/node1 zone-name set (`zoneRuntimeNameUnionAST`: every top-level `security` root plus the node0 and node1 group expansions) in compiled config metadata as `Config.ZoneQuarantineNames`, including tolerant compilation.
- Use that set, merged with the compiled config's own zones (`config.ZoneQuarantineNamesForConfig`), when deriving quarantine exclusions and when sanitizing node snapshots, so all node views agree on the collision winner.
- Add an isolated two-node regression: `z174` exists only in node0 and `z214` only in node1; both collide by stable zone ID. The test checks the set is retained by both compiled views, config exclusions drop only `z214`, and the peer snapshot records `z174` as survivor and removes `z214`.
- Update runtime consumers of quarantine-derived exclusions to use the same set.
- Refresh the #8892 snapshot-shape golden without a protocol bump: the new field is `json:"-"`, and the measured shape-walk delta against `51ace11d0` is exactly `ConfigSnapshot.Config.ZoneQuarantineNames []string "-"` (v45 STANDS).

## Risk

Tolerant loads quarantine the later-sorting colliding name on every node of a node-scoped pair. On a node whose only claimant of a shared ID is the loser, that ID gets no zone, no RG ownership, and a quarantine report naming a survivor that exists only on the peer. Operators must rename one zone to restore normal isolation.

Strict commits still reject every collision, including one involving a name only a groups block declares. In that case the lenient warning also still says the live zone is QUARANTINED, although runtime keeps it. Both are pre-existing on master; the zone counterpart of the #9657 routing-instance fix is a follow-up.

The partial-republish skew guard now also refuses a config whose runtime zone-name set differs from the applied one, until that config's full apply lands. This includes a change no quarantine depends on, such as a non-colliding zone added only to the peer's node group. The refusal retains the applied snapshot and retries, as for any other content change.

Other residuals:

- The compile-time validators that run before `ZoneQuarantineNames` is set still use the node's own zones (`compiler_validate_strict_zones.go`, `compiler_validate_warn_host_inbound.go`, `compiler_validate_warn_dhcp_hostinbound.go`, `dup_host_local_address.go`).
- `zoneNameByID` in session-sync requests still labels a shared ID with the local, quarantined name.
- During a rolling upgrade, nodes on old and new code disagree on node-scoped pairs.
- `configsContentEqual` still compares no other `json:"-"` field of `Config` or its nested structs, for example `QuarantinedRoutingInstances`, `SecurityConfig.UnknownPoliciesChildren`, or `StaticRoute.NoInstall`. Whether two configs can marshal equal yet differ in one of them has not been audited.

No live cluster was mutated.
