# #12246 — require post-DNAT input for policy matching

- **Timestamp**: 2026-10-08 (`fix/12246-campaign-pub`)
- **Action**: make the policy-only tuple-stage contract explicit wherever match-policies returns a verdict.

## Red before

At clean base `83b5c9553`, the VIP-vs-real fixture configured DNAT from `203.0.113.10:80` to `10.0.0.5:8080`, a VIP-permit policy, then a server-deny policy. The actual dataplane evaluates policy after destination translation (`policy_dst_ip = effective_resolution_target`), while `policymatch.Match` evaluates the literal tuple. `show security match-policies` therefore printed `permit-vip` for the VIP query without saying that the policy simulator had not translated it.

## Change

- The shared match-policies / test-policy usage text and `policymatch.Query` contract now specify that destination IP and port are expected as the post-translation tuple; the policy simulator does not perform NAT.
- `policymatch.Result.PostNATInputNote` carries the explicit requirement when inbound destination translation is configured. Local and remote CLI, REST JSON (`post_nat_input_note`), and gRPC (`post_nat_input_note`, field 31) surface it alongside the policy verdict.
- Added the VIP-permit/server-deny CLI regression and a shared usage/result contract table for DNAT, static NAT/NPTv6, NAT64, SNAT-only, and no NAT.

## Validation

- **GREEN after**: the focused CLI regression and `go test ./pkg/policymatch -run '^TestPostNATInputRequirement12246$' -count=1 -v` passed.

## Residual / risk

This change deliberately documents and reports the accepted post-NAT-input requirement; it does not implement DNAT translation in the policy simulator. A pre-NAT VIP query still evaluates the literal VIP policy tuple, but the returned note explicitly warns that the verdict is not the dataplane's post-translation decision. Operators must query with the translated server address and port, with the server's zone as to-zone.
