# Issue #12240 — retry rejected hold-drop publication

## Why

A hold-expiry drop updated manager state to empty before publishing it. When `onUpdate` rejected that apply, the old published hash remained and publication debt was visible, but later failed fetches skipped the drop transition because the feed no longer had a snapshot. The dataplane could therefore retain stale contents while the manager reported the feed dropped.

## What

The shared failure transition retries a hold-dropped feed's empty-state
publication on subsequent failed fetches while publication debt remains.
Recovery republishes identical last-good content after an unconfirmed
hold-drop because the rejected apply may have staged the dropped overlay.
The regressions cover retry/debt convergence, identical recovery, and
post-convergence no-thrash. The README documents this contract. Rejection
logs identify retries, use unconfirmed-state wording, and report accepted
retries. The #12241 periodic-failure test now waits for callback completion
after observing the dropped state, preserving its hold-timing assertion while
respecting the out-of-lock callback.
