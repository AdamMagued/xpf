# #12242 — accept any4/any6 in the strict policy gate

- **Timestamp**: 2026-10-08 (original change); R1 review fold 2026-10-12. Branch `fix/12242-campaign-pub` (PR #12457), one commit on base `83b5c9553`.
- **Action**: the strict policy-address checks and every downstream keyword classifier (the junos-host kernel projection and the #4146 warning predicates) use the SSOT keyword set, so `any4` / `any6` commit and behave exactly like `any-ipv4` / `any-ipv6`.

## Red before

- **Strict gate**: on base `83b5c9553` (the PR parent; the touched files are byte-identical to `a714c90d4`, where this was first measured), strict `CompileConfig` rejected a policy with source `any4` and destination `any6`: `source-address "any4" is not a defined address-book entry, the \`any\` keyword, or a valid CIDR/IP address`. The lenient compile kept both tokens with three warnings: the downgraded strict reject and two `not in address-book` advisories. A throwaway strict/lenient probe measured this; it was deleted and is not in the tree. `TestAny4Any6KeywordsReachTheWireAsLongFormCIDRs12242` was added before the implementation and failed with the same strict error.
- **Junos-host projection (R1 review)**: with only the strict gates widened (`21da243d9`), a committed `any4` reached the junos-host projection, which kept a private long-form keyword list. `any4` failed the literal parse, the term became unrepresentable, and the whole trust-zone program was withdrawn. A `source-address any4` deny projected `Representable=false` with no rules, behind only the #4168 advisory. A later permit spelled `any4` stripped the correctly spelled deny `p2` (NET9) of its kernel DROP and the #11065 terminal deny, so direct ssh from 10.0.9.0/24 fell back to the coarse permit-by-service gate. `junosHostPolicyStricterThanCoarseGate` and `junosHostAddrScoped` treated `any4` as a scope, which drew spurious #4146 warnings. On the tolerant channel, the resolver resolved an object named `any4` by name. The member gate's keyword arm and the #3958 warn-pass alignment had no pinning test.

## Change

- `policyMatchAddressTokenRecognized` (the #2008 strict gate, shared with the #3958 warn pass) and the #3149 member gate (`validatePolicyMatchAddressSetMembersStrict`) ask `IsPolicyAddressWildcardKeyword`. The empty token keeps its existing handling.
- `junosHostResolveAddrSet` classifies the empty token and every `PolicyAddressWildcardFamilies` keyword before the feed-taint and name lookups (the #9523 order). Its address-value keyword arm uses the same table. `junosHostAddrScoped` and the #4146 warning's `junosHostPolicySourceScoped` ask `IsPolicyAddressWildcardKeyword`.
- Not changed: the strict reject text still says "the \`any\` keyword". The edit would be cosmetic, and master rewrote the adjacent lines of `policyMatchAddressError`, so it would conflict. CLI completion still offers only the Junos spellings.

## Residual / risk

- `any4` / `any6` are xpf spellings, not Junos keywords. A config that uses them is not portable to Junos. A binary without #12242 rejects such a config at strict commit; its tolerant path still loads it, with warnings.
- The address-value keyword arm is reachable only by an `Address` built outside the compiler, because `looksLikeIPOrCIDR` never stores a keyword as a value.
- The eBPF compiler's `resolveAddrList` filters out only `any`. This is pre-existing, and both spellings behave the same there.
- No live cluster was modified.
